# Тестирование и сборка

Статус: план проверок согласованного MVP, 22.11.2026. Основное устройство — Samsung S25 Ultra; перед замером записать фактические Android, RAM, разрешение и режим производительности. Тестовые сборки, build entrypoints и CI пока **не созданы**. Команды ниже — инструкция для будущих этапов после появления тестов; успешные результаты текущему шаблону не приписываются.

## 1. Уровни проверки

| Уровень | Что проверять | Когда |
|---|---|---|
| EditMode | Расчёт урона/брони/доступности, инвентарь/лимиты, ключи, транзакции, DTO/migrations, reset rules, seeded loot, graph conditions | В каждой задаче с изменением правил |
| PlayMode | Коллизии, sword+wave, щит, движение/взгляд, сцены/переходы, pause, puzzles, AI/boss, runtime+save интеграция | При изменении поведения Unity |
| Editor validator | Уникальность ID, ссылки, граф, условия замков, награды, счётчики контента, spawn-зоны, policy согласованность | При каждом изменении данных и перед build |
| Android Development | Multitouch, safe area, lifecycle, kill, запись, frame time/память и профилирование | Начиная с S0, каждый этап |
| Release smoke | Установка, запуск офлайн, новое/продолжение, переход, бой, сохранение, отсутствие debug-команд | Каждый кандидат на выпуск |
| Внешний плейтест | Понятность и интерес, направление удара, обучение, время и причины смерти | S2, затем каждый храм и S6 |

Фиксировать seed, время, исходное состояние и ожидаемый результат. Не тестировать случайный дроп вероятностным ожиданием «за 100 убийств должно повезти»: проверить интервалы весов, сумму 100%, замены и границы HP через управляемый RNG. Таймеры проверять с подставным временем и допуском один шаг симуляции; интеграционные тесты отдельно доказывают соответствие реальному времени.

Для физики/телеграфов снимок состояния не заменяет визуальный мобильный тест. Скриншот не доказывает сохранность прогресса. Не нужен искусственный процент покрытия всего проекта: автоматикой обязательно покрыть критические инварианты прогресса и урона, а качество игры — плейтестом.

## 3. Локальное окружение

1. Установить через Unity Hub **6000.6.10f1** и Android Build Support с SDK/NDK/OpenJDK этой версии, проверить лицензию. Не открывать проект более новым Editor автоматически.
2. При клонировании проверить Git LFS: `.gitattributes` уже направляет изображения/аудио и другие бинарные файлы в LFS. Выполнить `git lfs install`, `git lfs pull` при наличии LFS-объектов; не коммитить указатели вместо отсутствующих ассетов.
3. Открыть корень проекта, дождаться восстановления пакетов из manifest/lock и импорта. Console без ошибок, Missing Script/asset; включены Visible Meta Files и Force Text (проверить, не считать настроенными заранее).
4. Сейчас стартовая сцена — `Assets/Scenes/SampleScene.unity`. После T02 запускать Bootstrap; после T06 выбирать созданный профиль Android Development. До этого кнопка Play показывает только шаблон.
5. Запустить EditMode и PlayMode через Window → General → Test Runner. Отсутствие тестов не означает зелёную приёмку.

`.env` в runtime не нужен: игра офлайн, конфигурация баланса хранится в definitions. `.env.example` сейчас не создаётся. Локальный путь Editor задаётся переменной PowerShell, секреты release/CI — защищёнными переменными CI и внешним keystore, никогда Assets/Resources/StreamingAssets.

## 4. Batch-тесты

### Статическая проверка T01

Из корня репозитория в PowerShell:

```powershell
./tools/Check-Baseline.ps1
./tools/Test-Baseline.ps1
```

Первая команда читает настройки, manifest/lock, meta и GUID-ссылки Assets/ProjectSettings,
а также доступные meta пакетов из Packages и Library/PackageCache. Она обнаруживает
неразвёрнутые LFS pointers; наличие Git LFS проверяется отдельно (`git lfs version`,
`git config --get filter.lfs.process`, `git check-attr filter -- <asset>`).
Вторая команда проверяет валидатор на изолированных временных данных и повреждённых
вариантах без установки пакетов. Ошибка проверки даёт исключение; при вызове через
`pwsh -File` процесс завершается с ненулевым кодом.

Это проверка файлов текущего каталога, не Unity EditMode/PlayMode и не content validator
будущих этапов. Она не проверяет fileID/subassets, Missing Script, полноту package restore,
сборку или чистый импорт. Кэш пакетов может содержать старые версии: окончательная
проверка ссылок и импорта выполняется в Editor. Результат T01 — в
[отчёте](reports/T01-baseline.md). При отсутствии HEAD нельзя выдавать `git lfs fsck`
за успешную проверку истории LFS. На текущем HEAD проверка прошла.

### Live-проверка T01

На открытом проекте сначала прочитать `console status`, сохранив cursor. Через Unity MCP
вызвать `script_eval` с `file: "tools/Verify-Baseline.cs"`, `timeout: 60`.
Альтернатива при доступном CLI:

```powershell
unity command script eval --caller plugin --skill unity-cli --project-path C:\Repository\likeZelda --file tools/Verify-Baseline.cs --timeout 60 --format json
```

Скрипт проверяет версию, завершение импорта/компиляции, сериализацию, Android target/support,
сериализованные ссылки ассетов и компоненты всех сцен через preview scenes, которые закрываются
в finally. Открытые рабочие сцены не сохраняются. PASS содержит путь проекта, счётчики и пути
SDK/NDK/JDK; перед приёмкой сверить путь с ожидаемым проектом. Затем проверить `console status`
и новые ошибки через `console get` с сохранённого cursor. Не очищать Console.
Скрипт находится вне Assets, не компилируется в Player и не является игровым EditMode-тестом.
Текущий результат: static PASS, 15 сценариев валидатора PASS, live PASS (37 объектов,
12 компонентов, две сцены), Console 0 errors / 0 warnings. Чистый checkout/build — T06.

### Unity Test Runner

После появления test asmdef команды запускаются из корня репозитория при закрытом Editor для этого проекта. Путь к Editor — пример стандартной установки, при другой установке изменить переменную. TestResults/Logs создаются и не попадают в Git.

```powershell
$unityEditor = 'C:\Program Files\Unity\Hub\Editor\6000.6.10f1\Editor\Unity.exe'
$projectPath = (Get-Location).Path
New-Item -ItemType Directory -Force TestResults, Logs | Out-Null
& $unityEditor -batchmode -projectPath $projectPath -runTests -testPlatform EditMode -testResults "$projectPath\TestResults\editmode.xml" -logFile "$projectPath\Logs\editmode.log"
& $unityEditor -batchmode -projectPath $projectPath -runTests -testPlatform PlayMode -testResults "$projectPath\TestResults\playmode.xml" -logFile "$projectPath\Logs\playmode.log"
```

Не добавлять `-quit` к тестам без проверки поведения runner: выход должен происходить после завершения тестов. Для графических PM-тестов не использовать `-nographics`. Два Editor-процесса над одним проектом одновременно не запускать. CI-обвязка должна дожидаться завершения процесса и проверять exit code, наличие XML, число тестов >0, отсутствие failed/errors и неожиданных skipped. Нулевой exit code без XML не означает успех.

## 5. Сборка

T06 создаёт проверяемые build entrypoints `AshBeacon.Editor.Build.BuildAndroidDevelopment` и `ValidateContent`; их **ещё нет**, команды `-executeMethod` сейчас не запускать. T36 добавляет `BuildAndroidRelease`. Entrypoint обязан валидировать каталог, установить явные сцены (Bootstrap, MainMenu, Gameplay), contentSet, platform/backend/architecture, output path и обработать BuildReport; ошибка даёт ненулевой exit code. VS и campaign собираются отдельными профилями.

В Editor: File → Build Profiles → Android, переключить платформу, проверить сцены, выбрать Development Build для тестового APK, выполнить Build And Run на USB debugging устройстве. Автоподключение profiler — только для замера; Script Debugging не включать в release. Release AAB настраивается после выбора application ID, signing и магазина; распространение APK/AAB не входит в текущую задачу.

Подпись: keystore вне репозитория, пароли передаются без вывода в лог; не в C# и не в committed ProjectSettings. Лицензионные данные Unity для CI также secret. Release без cheats, перехода к произвольной комнате и debug-флагов; проверяется сам итоговый Player, не только Editor define symbols.

## 6. Предлагаемый CI

Реализация базовой цепочки в T06; GitHub выбран по существующему origin, конкретный runner/лицензия уточняются перед настройкой. Пока workflows не добавлены.

PR: checkout + LFS → точный Editor и package restore → import/compile → EM → PM → content validator → development build при изменении runtime/ассетов. Чисто документальные правки: ссылки, согласованность ID, diff-check; Unity build без необходимости не запускать. Один job не должен делить открытый рабочий каталог с другим Editor. Cache Library привязан к Editor/OS/manifest/lock и не является источником истины.

Артефакты CI: XML, Editor/build logs, validation report, APK (для разрешённых запусков); время хранения предложено 14 дней, уточнить лимиты runner. Тестировать release-кандидат из чистого клона без Library cache. Не требовать побитового совпадения подписанных бинарников; воспроизводимость означает одинаковые входные версии, успешную сборку и одинаковые приёмочные результаты.
