План MVP, название «Пепельный маяк» и спорные правила согласованы владельцем 22.11.2026; решения и оставшиеся уточнения — `docs/decisions.md`. T00–T03 завершены. Владелец принял T03 28.11.2026: ввод, движение, взгляд и пауза реализованы, EditMode 11/11 и PlayMode 9/9 прошли. Результаты прогона на телефоне не зафиксированы. Доказательства — docs/reports/T03-controls.md. T04 завершена, подтверждение — docs/reports/T04-combat.md. Повторно согласовывать принятые решения не нужно. В проверочной комнате работают движение, меч, волна, здоровье и пассивный щит. По плану доступна T05. Двигаться по зависимостям tasks.md. Обновление до Unity 6000.6.10f1 выполнено владельцем, дальнейшие обновления самовольно не выполнять. Основной тестовый телефон — Samsung S25 Ultra, платформа — Android.

## Что читать перед задачей

3. `docs/roadmap.md`, строку задачи в `docs/tasks.md`, `docs/testing.md`.

При расхождении правил не переписывать требования по догадке. Зафиксировать конфликт через A/Q и согласовать изменение с владельцем. Исходный GDD сохраняет точные параметры и реестры. Утверждённые изменения одновременно отражать в GDD, FR/NFR, задаче и тестах.

## Рабочий цикл SDD

- Выбрать одну доступную задачу с выполненными зависимостями. Записать короткую спецификацию: цель, ссылки на FR/NFR, поведение/ошибки, границы, критерии, тесты и риски.
- Неоднозначности фиксировать до реализации зависящего поведения. Неблокирующие вопросы не должны останавливать независимую работу.
- Реализовать минимальный объём задачи, добавить содержательные тесты правил и интеграции. Не создавать заранее пустые системы для всей кампании.
- Выполнить подходящие проверки из testing.md. Сбой среды или непройденная ручная проверка — явный статус, а не «всё работает».
- Обновить статусы, spec и отчёт этапа: что сделано, что проверено, что не проверено, ограничения. DONE только по доказанным критериям.
- Расширение объёма, смена движка/архитектуры/правил требуют записи решения. Не добавлять новую механику ради удобства реализации.

## Инженерные ограничения

- Editor 6000.6.10f1, пакеты — manifest + lock. Без самовольных обновлений/установок. Не переносить проект на другую версию при открытии.
- Domain/Application — чистый C#, без UnityEngine. UnityAdapters обслуживает физику, ввод, представления; Infrastructure — файловое хранение. Явная композиция; не использовать глобальный singleton для всей игры.
- Баланс и контент в definitions. Runtime не мутирует ScriptableObject. UI читает состояние, не хранит вторую копию HP/денег/ключей.
- Уникальные ID контента постоянны, не генерируются заново при запуске. Дверь с двух сторон имеет общий флаг. Для среза `VS-*` отдельный contentSet и сохранение.
- Каждый объект имеет явную reset policy. Транзакции наград, покупок, дверей и босса не разбивать на независимые сохранения.
- Не менять правила, защищающие от тупиков: ключ до замка, стрелы на обязательном пути, сброс блоков, безопасный spawn, возврат ко входу, отсутствие дублей.
- Time/RNG/storage должны допускать тестовую подмену. Пауза останавливает бой/ИИ/ловушки; UI остаётся работоспособным.
- Runtime-ресурсы, лицензии ассетов и платные сервисы не добавлять без основания в задаче. Никаких обязательных сети/аккаунтов/аналитики в v1.

## Unity и Git

- Сначала проверить `git status`; чужие и незакоммиченные изменения не удалять и не перезаписывать. Не делать reset/clean/revert чужой работы.
- Assets переносить вместе с `.meta`, предпочтительно через Editor; существующие GUID не пересоздавать. Новые Unity-ассеты импортировать до коммита, чтобы появились корректные `.meta`.
- Force Text и Visible Meta Files проверять в T01. Сцены/prefab редактировать минимально, избегать массового пересохранения.
- Хранить Assets, Packages (включая lock), ProjectSettings и docs. Не хранить Library, Temp, Logs, Builds, результаты тестов, локальные сохранения и секреты.
- Уважать существующий `.gitattributes`/LFS. Бинарники перед коммитом должны быть доступны, не только LFS pointer.
- Не коммитить keystore, пароли, токены, лицензии Unity. Не добавлять секреты в `.env.example` или клиентские Assets.
- Пуш, merge, публикация и релиз не подразумеваются задачей разработки. Выполнять их только при соответствующем поручении.

## Проверка и отчёт

Изменения логики: релевантные EditMode; интеграции/сцен — PlayMode; контента — validator; управления/lifecycle — Android. На документальные правки достаточно проверки ссылок, ID, согласованности и diff; не писать тест, который лишь повторяет текст документа.

Проверять исходный сценарий и отрицательный случай: повтор награды, пустой запас, закрытый путь, потеря фокуса, прерывание записи. Для каждого этапа нужен воспроизводимый результат, а не только скриншот.

Документы и объяснения — на русском, названия кода — на английском, namespace `AshBeacon`. Ответ: сначала результат, затем проверка и существенные ограничения. Не объявлять неподтверждённое поведение выполненным. Следующий шаг должен соответствовать согласованной дорожной карте.
